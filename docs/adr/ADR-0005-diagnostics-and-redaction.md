# ADR-0005：诊断包与脱敏（可发送、可信任）

- 状态：已采纳（第 38/39/40 轮）
- 关联轮次：第 32、38、39、40 轮

## 背景

用户报 bug 时，维护者需要问十轮：什么系统？Java 几？装了什么 Mod？
用的哪个源？日志在哪？——每次排查的时间成本远高于问题本身。
同时，诊断材料里天然混有敏感内容（OAuth 令牌、设备码、Windows 用户名、
带凭据的代理地址），用户"不敢发"与"发了泄露"都是失败。

## 决策

1. **一键诊断包**（设置 → 导出诊断包），内容六类正好覆盖十轮问答：
   最近 3 个日志、config.json（脱敏）、系统信息（OS/架构/内存/.NET）、
   Java 清单、实例概览（版本/加载器/Mod 数量与最近 Mod）、最近 20 条
   安装/下载记录。
2. **脱敏三原则**：
   - **替换而非删除**——保留字段结构，排查时能看出"字段存在但值为空"；
   - **全文本覆盖**——包内所有文本文件统一过正则（令牌形 JSON 字段含
     device_code/refresh_token/user_hash、Bearer 令牌、`user:pass@host`
     代理凭据、`C:\Users\<名>` 用户路径、启动器根路径），而非只处理
     config.json；
   - **附脱敏报告**——包内 `redaction-report.txt` 逐文件记录替换了哪些
     模式、各多少处。用户看到"你的令牌字段被替换了 3 处"，就会敢发；
     误伤也能立刻被发现（如 Mod 名恰好含 "token" 不会被误伤——
     字段形正则要求冒号结构）。
3. **大小可控**：日志**尾部截断**，每文件最多保留末尾 2MB
   （崩溃行在日志末尾——方向经单测锁定：末尾的关键崩溃行必须存活，
   头部丢弃并标注"仅保留末尾部分"）。
4. **崩溃规则翻译**：`CrashRule(Pattern, Title, Suggestion)` 只读列表
   （加规则只改一处，结构为未来外部规则包留口子）；匹配大小写不敏感；
   专项规则（loader/mod）优先于泛化 JVM 规则；崩溃摘要自动附
   "可能原因"行——把排查经验固化进产品，输出的是人话而非退出码。

## 后果

- 正面：报 bug = 发一个 zip + 崩溃摘要；脱敏报告建立"敢发"的信任；
  常见崩溃（Java 过低 / OOM / 重复 Mod / 缺前置）用户自查即可解决。
- 代价：正则脱敏理论上存在误伤（如路径恰好匹配用户名模式）——
  已由单测锁定边界（Mod 名含 "token" 不误伤、非用户路径不误伤），
  且脱敏报告让任何误伤可见。
- 边界：截断方向必须"保留尾部"已由单测锁定（`TruncateTail` 纯函数）；
  未来若改为"保留头部"，测试会立刻失败。

## 反例（不采纳此 ADR 的已发生后果）

第 32 轮用户报告"游戏崩溃提示看日志，点开日志页卡死无响应"——
日志集合被 Trace 级输出灌爆（4000+ 行无上限）。第 32 轮修复后
（过滤 Trace + 上限 + 批量派发 + 虚拟化修复），日志页秒开；再配合
文件日志 `[Game]` 行与崩溃摘要，第 33-34 轮两次崩溃（缺 `-cp`）均由
用户直接贴日志定位，未额外提问——诊断链路的收益已被实证。
