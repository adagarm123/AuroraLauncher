# ADR-0014：启动前判定「加载器与整合包是否真的存在」

- 状态：已采纳（第 92 轮，含防线测试）
- 日期：2026-11-15
- 相关：[ADR-0011](ADR-0011-download-residue-and-integrity.md)（下载完整性）、[ADR-0012](ADR-0012-storage-cleanup-allowlist.md)（存储清理）

## 背景

用户导入了一个 Forge 整合包，只装好了原版部分。之后每次「启动游戏」都成功，进游戏却是纯原版 —— 没有加载器、没有模组，启动器从未提示。

对着真实数据核查后，是四个独立缺陷叠在一起：

1. **`NeedsRepair` 只问原版**：`ResolvedVersionId` 为 null 时回退到 `MinecraftVersion`，只校验原版文件。加载器从未安装这件事，没有任何检查覆盖。
2. **没有「应该有什么」的记录**：导入 `.mrpack` 时不记预期模组数，`mods/` 空着也永远判完整。
3. **元数据没落盘**：导入路径里 `InstallWithLoaderAsync` 填好的 `ResolvedVersionId` 没有 `Update`，重启后丢失。
4. **健康判定只看内存**：`PeakMemoryMb=2` 是采样器只采到 `java.exe` stub 的读数，却与 `-Xmx` 比较后输出「健康」。

## 决定

### 1. 把「装好了没有」变成一个纯函数

`LaunchReadiness` 只接收事实（加载器类型、原版 id、ResolvedVersionId、profile 是否存在、原版文件是否完整、整合包扫描结果），返回：

- `LoaderNotInstalled`（**不可覆盖**）—— 加载器实例必须有「加载器形态的 id + 该 profile 真实存在」。`ResolvedVersionId` 为空或等于原版 id，都算没装。
- `ModpackEmpty` / `ModpackPartial`（**可覆盖**）—— 用户有权在清楚风险时说「仍然启动」。
- `CoreFilesMissing`（不可覆盖，可修复）。

理由：判断逻辑必须能在没有文件系统、没有 UI 的情况下被穷举测试。UI 只负责把结论翻译成对话框，不再各自判断。

### 2. 预期在下载之前落盘

导入 `.mrpack` 时**先**写两样东西，再开始下载：

- `instances.json` 里的 `IsModpack` / `ExpectedModCount` / `ExpectedFileCount`；
- `instances/<id>/modpack-manifest.json`（每个文件的相对路径、URL、SHA-1、大小）。

这样导入中途失败留下的实例是**可识别的**，而不是一个看起来正常的空壳。清单同时是「补全」的依据：原始 `.mrpack` 不在了也能按 URL 重下。

### 3. 只拦「明显没装完」，不拦个人口味

`mods/*.jar` 的实际数量决定结论：

| 实际 / 预期 | 判定 | 行为 |
|---|---|---|
| 0 / N (>0) | Empty | 拦住，说明应有数量 |
| ≥1 且 ≤ 一半 | Partial | 拦住，报「实际/应有」 |
| 少一两个 | Complete | 不打扰（用户可能故意删了模组） |
| 预期 0 | Complete | 纯配置包是合法的 |

「少一半以上就拦」是刻意选的阈值：它覆盖了「下载到一半断了」，又不会因为用户裁掉两个可选模组而每次启动都弹窗。

### 4. 加载器缺失不可覆盖

`LoaderNotInstalled` 不给「仍然启动」。加载器没装上的 Forge 实例，启动起来就是另一个游戏 —— 用户点的是「启动这个整合包」，不是「启动一个原版」。这种「安全」只有一条正确出路：补全；补不上就说明原因（网络/镜像 404）。

### 5. 运行结果必须带退出码

`LastExitCode` 随性能快照一起落盘，`PerformanceReport.RunVerdict` 按以下顺序判定：退出码非 0 → 异常退出；活不过 3 秒 → 闪退；峰值 < 10 MB（JVM 不可能这么小）→ 未采集到；再比内存与 FPS。**宁可说「未采集到」，也不编一个数字。**

采样线程改为专用 `Thread`（首采样等 1.2 秒，绕开 stub），并把「采样次数 / 首采样 / 峰值 / 时长」写进日志 —— 上一轮"2 MB"之所以难查，就是因为一行证据都没有。

## 被否决的方案

- **只补 `NeedsRepair` 一处**：能拦住加载器缺失，但拦不住「加载器装好了、模组一个没下到」——那正是用户遇到的第二种表现。
- **用 `.mrpack` 文件的哈希判断装完没有**：`.mrpack` 常常是临时下载的，用户删掉它之后就无法判断。
- **每次都按清单全量校验哈希**：300 个模组、几个 GB，启动前扫一遍要几十秒。改为「存在 + 尺寸相符」，哈希交给下载引擎。
- **加载器缺失也允许「仍然启动」**：等于把「启动整合包」静默替换成「启动原版」，是这轮要消灭的行为本身。

## 后果

- 老实例（第 92 轮之前导入、没有清单）无法被校验，只能重新导入；启动时会给一条非阻塞提示（`mods` 为空且有加载器）。这是有意的取舍：宁可少一条自动检查，也不猜用户装了哪个包。
- 每次启动会多几次目录枚举（`mods/*.jar` 计数 + 清单存在性），实测可忽略。
- 「补全」现在会重新下载缺失的整合包文件；用户手动删掉的模组会被补回来 —— 与「补全」的语义一致，帮助主题已写明。

## 防线

- `#116` 模组数与清单双口径（含空包、少一两个、半截文件）
- `#117` 闸门策略 + **真实 `LauncherService` 路径**（`ResolvedVersionId=null` 的 Forge 实例必须 `NeedsRepair=true`）
- `#118` 运行判定（异常退出 / 闪退 / 未采集 / 吃紧 / 健康）
- `#119` 源码守卫：`BuildLaunchSpecAsync` 必须有加载器检查；`NeedsRepair` 必须覆盖加载器与整合包；启动流程必须先过闸门再预检；采样不得退回 `Task.Run`；预期必须在下载前写入
- `--launch-gate-smoke`：真实 VM 点「启动游戏」，断言被拦住、日志中没有 `Launching:` 命令行
