# ADR-0006：崩溃自动修复的安全边界（能动手，但只碰自己的东西）

- 状态：已采纳（第 78 轮）
- 关联轮次：第 60（崩溃卡片）、70（导出日志）、77（模组体检 / 补全文件）、78 轮

## 背景

第 60 轮的崩溃卡片只回答"可能为什么崩"，用户仍要自己去设置页改内存、
去官网找 Java、去 mods 里翻重复项。把"翻译"升级成"修复"很自然，但一旦
程序开始**替用户改东西**，风险等级就变了：一个判断失误的自动修复可能删掉
存档、删掉模组、改掉系统环境变量，或者让用户在不知情的情况下失去数据。

同时还有一个反向风险：**承诺了却修不好**。例如机器只有 4 GB 物理内存，
却"自动把 -Xmx 提到 8 GB"——崩溃只是从游戏里搬到了操作系统里。

## 决策

1. **修复动作是一个封闭枚举**（`FixAction`），没有"删除 / 移动 / 改环境变量 /
   提权"这类成员。想加一个危险动作，必须先改枚举——而枚举名会被 Guard 扫描
   （禁 `Delete / Remove / Kill / Env / Format / Overwrite / Admin`）。
2. **自动修复的配置足迹是白名单**：`AffectedConfigKeys` 只允许
   `MaxMemoryMb / MinMemoryMb / JavaPath`。其它动作只能"只读扫描"或
   "向实例下载文件"（Fabric API、补全缺失文件）。
3. **三态而不是两态**：`Auto`（启动器直接做）/ `Guided`（只打开 mods、
   shaderpacks、saves、驱动页、账户区，由用户决定）/ `Info`（仅说明）。
   凡是"需要判断用户意图"的（删哪个模组、移哪个光影），一律 Guided。
4. **修不好就明说**：物理内存没有余量时，`SuggestHigherMemory` 返回
   `Useful=false`，动作降级为"去设置调整内存"并解释原因；Java 版本则先找
   本机已装的大版本，能复用就绝不重下。
5. **求助邮件不由程序发送**：只生成 `mailto:`（正文含诊断 / 已尝试的修复 /
   诊断包路径），由用户在**自己的**邮件客户端里确认并发送。启动器不持邮箱
   凭据，因此不可能被滥用成垃圾邮件源，也不会偷偷上传日志。
6. **不占界面线程**：诊断（600 行 × 27 条正则）在 `Task.Run` 内，修复全部
   `await`。游戏刚崩，窗口必须还能点。

## 后果

- 正面：高频崩溃（OOM、Java 版本、缺 Fabric API、文件损坏）从"看建议"变成
  "点一下"；用户仍然对"删什么"拥有完整决定权；修复行为可解释、可回滚
  （内存/Java 都能在设置页改回）。
- 代价：自动化程度被刻意压低——比如"重复模组"永远只能打开文件夹，
  因为无法证明删哪一个不会破坏整合包。这是有意为之的保守。
- 防线：三条测试锁定（#80 配置键白名单 + 枚举名扫描、#82 源码禁令 +
  后台线程检查、`--crash-smoke` 真实渲染并验证"点一下真的改了配置"）。

## 反例（如果不这么做）

- 若允许"自动删除冲突模组"：用户 A 的两个模组互相 `breaks`，删掉其中一个后
  存档里的方块 ID 全部错位——数据损失不可逆。
- 若允许"自动把 -Xmx 提到物理内存上限"：4 GB 机器上崩溃从 `OutOfMemoryError`
  变成整机卡死，用户连日志都拿不到。
- 若程序内嵌 SMTP 凭据自动发信：凭据随二进制分发即泄露；且任何一次误判都会
  让作者邮箱被自己的程序轰炸。
