# ADR-0023 更新进度可见、可取消与首次引导的存储选择

- 状态：已采纳（含静态防线与离线单测）
- 轮次：第 101 轮（2026-11-17）
- 触发：用户反馈「自动更新时没有弹窗显示更新进度，也没有可取消选项」「首次引导要在下载文件前让用户选是否把启动器所有文件放到 EXE 目录」。

## 背景

第 61 轮已经把**安装/换装**阶段做成了可见窗口，但**下载**阶段只在设置页更新一条进度条；自动下载模式甚至只弹一句 toast。用户看到的是「启动器好像不动了」，而且没有任何取消手段。

第 99 轮的首次引导确有便携勾选，但它混在「检查 Java」页里，与真正的下载步骤隔了一屏，用户没有把它识别为「下载前必须做的选择」。

## 决策

1. **下载阶段独立弹窗，状态单一来源。** 新增 `UpdateDownloadWindow`，所有三条下载路径（自动下载 / 提醒后更新 / 手动检查）都调用 `PrepareUpdateWindow`。窗口绑 `UpdateProgress`、`UpdateProgressIndeterminate`、`UpdateStatusText` 三个 VM 属性，与设置页完全同源，不做第二套计数。
2. **取消是真取消，不是隐藏窗口。** `CancelUpdateCommand` 走 `_updateCts`；关闭窗口也调用同一个 `CancelUpdate()`。只有 `UpdateUiPolicy.CanCancel(active, requested)` 为真时按钮可用，连点不会竞争。
3. **取消的边界写清楚。** 若本次下载之前没有可用暂存，取消调用 `UpdateService.CancelStagedDownload()` 清掉 patch / merged / staged exe / staged info；若之前已有「已就绪」更新，则**不清理**，并明确告诉用户旧更新仍可应用。文案与判定集中在 `UpdateUiPolicy`，可离线测试。
4. **换装阶段保持不可取消。** 替换正在运行的 EXE 时强关进程会留下损坏文件；`UpdateApplyingWindow` 底部直接写明原因，不提供假按钮。
5. **首次引导改为 4 步，存储选择独占第 2 步。** 步骤 1 检查 Java 时不再顺手写便携标记；步骤 2 用两个互斥选项（系统默认 / 全部放 EXE 目录）并展示真实路径，下一步才进入下载步骤 3。判定走 `FirstRunStoragePolicy.ShouldCreateMarker`，只写 `portable.txt`，不搬移已有文件，重启生效；跳过引导不写标记。

## 权衡

- 自动下载模式本来是「不打扰」设计，现在弹窗会打断用户；这是用户明确要求的取舍——看得见状态优先于零打扰。
- 取消下载清掉暂存是为了不留下「看似完成其实不可用」的更新；用 `hadStagedBefore` 保护旧暂存，避免把用户已经下载好的版本误删。
- 引导多一步会增加一次点击；换来的是「所有文件放哪儿」在法律/隐私敏感场景（U 盘、共享电脑）里变成一个被明确确认过的选择。

## 验证与已知限制

- `--unit` 166/166、`--all` 173/173；新增 4 项涵盖进度文案、取消可用性、存储路径策略及 2 条静态 Guard。
- 只做了代码与静态防线层面的验证；**弹窗的实际观感、取消后的磁盘清理、首次引导四步的真实点击流程仍需用户实测**。
- 更新窗口没有做「最小化到后台继续下载」；取消是唯一的退出方式，避免再引入一套状态。
