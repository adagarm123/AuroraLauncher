# ADR-0012：存储清理的允许清单与"空壳"判定

- 状态：已采纳（含防线测试 #106–#110）
- 日期：2026-11-14（第 88 轮）
- 相关：ADR-0011（残留归属与完整性）、ADR-0009（实例删除与对账）、`DataRootPolicy`（第 84 轮）

## 背景

数据目录会自己长大：图标缓存、安装器缓存、版本清单、日志、`update/` 残片、下载残片、安装失败留下的空版本目录。单靠"手动进文件夹删"是不现实的——用户分不清哪个目录能删，而删错一次就是存档没了。

第 87 轮已经做掉了"下载残片"这一块，并建立了归属模型（`ActiveDownloads` + `DownloadJournal`）。这一轮把它扩展到整个目录，于是风险从"删不干净"变成"**删多了**"。

## 决策

### 1. 只写允许清单，不写禁止清单

`StorageCleanupPolicy.IsAllowedPath(root, path)` 是**唯一**的判据，而且是白名单：

| 允许 | 说明 |
|---|---|
| `cache/icons/**`、`cache/optifine/**`、`cache/installers/**` | 纯缓存 |
| `cache/version_manifest_v2.json` | 单个文件 |
| `update/**`，但排除 `AuroraLauncher.new.exe` 与 `build-info.txt` | 待安装的包不是垃圾 |
| `logs/aurora-*.log` | 只认 `Logger` 的命名 |
| `versions/<id>`（只到这一层） | 目录本身，内容不逐文件删 |
| `libraries/**`、`assets/**` 里的 `.part` / `.tmp` | 半截文件永远不是 payload |

拒绝（不列举个别例外，而是整棵树都不在名单里）：`instances/`、`backups/`、`java/`、`config.json`、`instances.json`、`accounts.json`、下载台账、数据根自身、数据根之外的任何路径。

**为什么是白名单**：如果写成"禁止 instances/backups/…"，那么新增一个目录（比如以后的 `snapshots/`）默认就是可删的——忘记加一条禁令就会悄悄出事。白名单则相反：新目录默认不可删，想删必须显式加规则，而加规则会被守卫测试盯住。

**一处刻意的偏离**：题目把 `libraries/`、`assets/` 列进"不碰"。这里的实现是"**payload 不碰，`.part`/`.tmp` 可以清**"。理由：`.part` 不是被引用的对象，它只是下载中途的半成品；而第 87 轮的残留清理本来就会删它们，两个入口对同一类文件给出不同答案只会让人困惑。守卫测试同时锁死了另一面——`libraries/…/foo.jar`（无 `.part`）必须被拒绝。

### 2. "空壳版本目录"必须窄到几乎不会误伤

判定：目录里**既没有 `<id>.json` 也没有 `<id>.jar`，并且递归下来一个文件都没有**。

任何文件的存在都会让它被跳过，哪怕只是 `natives/` 里的一个 dll——半装状态可能是用户正准备用「补全文件」修好的。删除前**再判一次**：扫描结果是快照，用户可能看了几分钟才点确认，这期间文件可能已经被装进去了。

### 3. 会牺牲离线能力的项永远默认不勾

`CleanupCategoryInfo.DefaultSelected` 是唯一来源，UI 的勾选状态由它初始化（`_selected = group.Info.DefaultSelected`）。守卫测试断言所有 `CostsOffline` 分类为 `false`，并且断言 VM 里出现的是这个字段而不是硬编码——否则以后有人"顺手"把加载器缓存也勾上，用户的离线兜底就没了。

### 4. 图标缓存搬进数据根

`IconCache` 原来把图片写在 `%TEMP%\AuroraLauncher\icons`。三个问题：存储清理看不到它、多个数据根共用一份、Windows 的「存储感知」会把 `%TEMP%` 当垃圾清掉。改到 `cache/icons` 后，"清理图标缓存"才真的有一个可清且可解释的对象。旧目录不主动删除（系统临时目录不归启动器管）。

### 5. 交互与第 84 轮一致

扫描 → 报告（分类 · 数量 · 大小）→ 勾选 → 确认（写明项数、体积、不可恢复，默认「否」）→ 执行 → 如实报告（释放量 / 被占用未删除数 / 剩余项）。两个清理入口共用同一套残片归属判定，因此同一批文件不会出现"一个说能删、一个说不能"。

## 后果

- 扫描要遍历整个数据根（assets 常有上万个文件），实测约 300 ms 量级；因此只在用户点按钮时跑，不在启动时跑。
- 删除是逐文件 + 逐已知目录，速度受文件数影响；`cache/icons` 少则几十、多则几百个文件，可接受。
- 被占用（杀软、正在运行的安装器）的文件会失败并被计数，不阻塞其余文件，也不假装成功。
- `versions/` 的清理与第 9/84 轮的"未引用版本 GC"职责分离：GC 删的是**有** json/jar 但没人引用的版本（删除实例时触发），这里删的是**什么都没有**的空壳。

## 复核修正（第 89 轮）

第一版实现有三处"看起来对、其实留了口子"的地方，复核后补上：

1. **`VerifyHash(` 的禁令原来只扫 `DownloadEngine.cs`**。第 86 轮的安装器清残留逻辑在 `ModLoaderInstallers.cs`，那里如果再引入一次旧判定，守卫不会响。规则针对的是**标识符**，不是某个文件，所以扫描范围必须是整个 `src/`；唯一豁免是 `DownloadIntegrity.cs` 里解释"旧实现为什么有问题"的注释，并额外断言那个文件不得重新定义该方法。
2. **删残片没有同步台账**。重放规则（`.part` 不存在就忽略）让这件事不出错，但记录会留在日志里直到下一次压缩——而压缩只在启动时发生。现在两个清理入口删掉台账内的残片时写一条与引擎完成时相同的 `-` 记录，并重新加载下载页的续传横幅。**一个文件被删除后，所有引用它的地方都要一起更新**，这条和第 84 轮"删除实例先删文件再删记录"是同一条原则的两面。
3. **"点下去没反应"的风险**。清理可能涉及上万个文件，而原实现只有一个静态文案 + 一个禁用状态。现在按钮文案随状态切换（`清理选中项` → `清理中…`）、列表勾选冻结、加上不确定态进度条；报告整体替换而不是逐项插入。

另外补了一条 UI 文案义务：**两个清理入口的分工必须写在按钮下面**。它们删同一批残片时判定一致（都走 `DownloadResidue`），但入口不同、代价不同，不写清就一定会有人问"这两个按钮有什么区别"。

## 被否决的方案

- **递归删除 `cache/` 整个目录**：`cache/` 里有下载台账（`download-journal.log`），删掉会丢失断点续传信息。逐文件 + 白名单更安全。
- **把 `.part` 的判定复制一份到这个服务里**：会出现两套归属规则，早晚上演"两个按钮说法不一致"。复用 `DownloadResidue`。
- **对所有分类都默认勾选，只靠确认框兜底**：用户点"是"的速度远快于读文案；默认值本身就是一种承诺。
- **按目录修改时间推断"空壳"**：一个刚创建 3 秒的目录可能是正在安装的版本；只看"有没有文件"才是确定性的。
