# ADR-0011：下载残留的归属判定与「完整性」语义

- 状态：已采纳（含防线测试 #100–#105）
- 日期：2026-11-14（第 87 轮）
- 相关：ADR-0010（下载线路策略）、`DownloadJournal`（第 74 轮）、`PathWriteGate`（第 73 轮）

## 背景

两件事凑到一起，成了同一个问题的两面。

**其一，「没有校验值」被当成了「文件没问题」。** `DownloadEngine` 里原来的判定是：

```csharp
if (string.IsNullOrEmpty(expectedSha1)) return true;   // VerifyHash(null) == true
```

于是凡是没有 SHA-1 的条目（OptiFine、第三方 CDN、老格式库）都自动"校验通过"。缓存命中判断用的正是它，所以一个写到一半的 jar（磁盘满、连接被掐、复制中断）会被一直当成"已经下好了"，直到启动时才崩，而且报错完全看不出原因。第 86 轮修 Forge 安装器时已经绕开过一次（下载前显式删残留），但那是补丁，不是修复。

**其二，`.part` 文件只进不出。** 下载被打断就留下半截文件；`DownloadJournal` 只负责"崩溃后能续传"，没有任何清理路径。用户能看到"磁盘少了 68 MB"，却不知道是谁占的，而且手动去文件夹里删很危险——他分不清哪个 `.part` 还能续传。`update/` 更糟：那里的 `.patch` / `.merged.exe` / `.part` 从不入台账，中断一次就永久留下。

## 决策

### 1. 完整性判定拆成"三问"，并把"无法确认"单独列出

`DownloadIntegrity.Check(path, expectedSha1, expectedSize)` 返回四态：

| 结果 | 条件 |
|---|---|
| `Match` | 有哈希且相符，或没哈希但声明大小相符 |
| `Mismatch` | 有可比的基准且不符（**截断文件在这里被抓住**） |
| `Unverifiable` | 既无哈希也无大小 —— 不知道，不等于"好" |
| `Missing` | 文件不存在 |

两个调用点用不同的规则，因为它们的处境不同：

- **缓存命中**（目标文件已存在）：只有 `Match` 才允许跳过。`Unverifiable` 一律重下——多花几 MB 流量，换掉"留一个坏文件"的风险，这个交换划算。
- **刚下载完**（我们写的 `.part`）：只有 `Mismatch` 才算失败。`Unverifiable` 必须放行，否则重试会无限循环（没有东西可比，重下多少次都一样）。

**为什么还留一个"大小"这一级**：很多源只公布大小。没有这一级，`Unverifiable` 会把本来能判断的情况也推给重下——那是对流量的浪费，也是对用户时间的浪费。

**一个必须记住的坑**：`HttpClientFactory` 开了自动解压（gzip/brotli），磁盘上的字节数 ≠ 元数据里的声明大小（后者算的是线上字节）。所以只有响应**没有** `Content-Encoding` 时才做大小比对；有压缩就交给哈希，没哈希就 `Unverifiable`。

### 2. 归属由引擎登记，而不是由清理器猜

清理器要回答的唯一问题是"这个 `.part` 现在有人用吗"。它不能靠任务列表猜：`DownloadJob` 不知道自己会下哪些文件。也不能靠 `PathWriteGate` 判断：门只说"有人排队"，不说"有人在写"。

所以引入 `ActiveDownloads`：引擎在开始处理某个目标文件时 `Register(dest)`，完成/失败/取消时释放（引用计数，因为两条流水线可能真的要同一个库）。登记覆盖**整个文件操作**，包括重试之间的退避等待——那期间 `.part` 仍然归它。

清理器据此把每个 `.part` 分成三类，并给出**不同的处置**：

| 归属 | 含义 | 处置 |
|---|---|---|
| `ActiveTask` | 有个活任务正在写 | **绝不删**，报告"保留 N 个" |
| `Journaled` | 台账里有、但没任务在跑（＝下载页还能续传的那些） | 可删，但**先问一句**（默认"否"） |
| `Unowned` | 没人认领（<4 MB 未入台账、`update/` 残片） | 直接删 |

### 3. 分批次的阈值提示，而不是每次启动都弹

只有"攒多了"才值得打扰：默认 **> 200 MB** 或 **> 50 个文件**（任一维度）。两个维度都要，是因为两种形态都异常——20 个 300 MB 的残片，和 400 个 1 MB 的碎屑。阈值放配置里（`residueWarnBytesMb` / `residueWarnCount`），0 = 关闭该维度，两个都 0 = 彻底不提示。提示是非阻塞的一条横幅，带「去设置清理」和「知道了」（后者只对本次运行生效，不删任何东西）。

### 4. `update/` 用"年龄 + 豁免集"，不用"年龄"

`UpdateStaging` 清掉 `update/` 里超过 24 小时的文件，但 `AuroraLauncher.new.exe` 与 `build-info.txt` 按**路径**豁免，与年龄无关。理由：那是"下次启动要装的包"，如果用户两天没关启动器，按年龄清掉它等于静默取消更新。

## 后果

- 没有校验值的条目在缓存命中时可能多下一次（换掉"坏文件被当成品"的风险）。这是有意的取舍，已在 README 里写明。
- 清理按钮是**不可撤销**的（删的是临时文件），所以可续传的部分必须先确认；`Unverifiable` 的语义也意味着"没有校验值的文件不会因为存在就被跳过"，安装流程会稍慢一点。
- 三个新守卫锁住了容易退化的地方：`VerifyHash(` 不许回来、缓存命中必须走 `IsTrustworthyForSkip`、每个文件操作必须 `Register`、`update/` 清理必须带豁免集、扫描与删除必须离开 UI 线程。

## 被否决的方案

- **在 `DownloadFileAsync` 里同步测速/扫描**：第 69 轮的教训（同步 I/O 卡 UI 48–218 ms）直接否决。
- **把 `Unverifiable` 一律当失败**：没有哈希的条目会永远下不完。
- **启动时直接删无主 `.part`（不提示）**：一旦判错（例如把某个正在启动的下载的 `.part` 当无主），用户会丢进度且不知道发生过什么。提示 + 手动按钮把决定权交回用户。
- **用任务列表推断归属**：`DownloadJob` 不含文件清单，推断必然漏；由引擎登记是唯一可靠的事实来源。
