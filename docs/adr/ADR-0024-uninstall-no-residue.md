# ADR-0024 卸载残留根治（本体 / 文件 / 注册表）

- 状态：已采纳（含静态防线与离线单测）
- 轮次：第 102 轮（2026-11-17）
- 触发：用户反馈「一键卸载后启动器本体仍存在」「卸载后仍有文件、注册表残留」。

## 背景

第 99 轮的一键卸载把运行中的 EXE 交给 `MoveFileEx(DELAY_UNTIL_REBOOT)`，于是用户卸载完立刻去看文件夹，本体还在——它要等重启。清理范围也是一份固定白名单，只覆盖数据根下的条目；注册表从未处理。第 99 轮因此明确写了「未在真机执行卸载」，这次的反馈正好来自真实执行。

## 决策

1. **临时清理进程取代重启等待。** 卸载时把当前 EXE 复制到 `%TEMP%`，以 `--uninstall-cleanup <manifest.json>` 无窗口启动。它等父进程真正退出（最多 15 秒轮询），再删原 EXE 与清单里仍存在的文件。`App.OnStartup` 在任何窗口/配置/单实例逻辑之前接管该参数，`ShutdownMode=OnExplicitShutdown`。
2. **清单可篡改也删不到别处。** 清理进程对每个路径调用 `UninstallService.IsCleanupPathAllowed`：必须在数据根内且目录/文件名命中启动器白名单。清单本身只由主程序写，包含的资源都是用户已确认过的 `UninstallPlan.Targets`。
3. **回退路径诚实。** 临时进程启动失败时，才调用 `DeferExeUntilReboot`（重启后删除），并在完成弹窗里明确写出「不是立即删除」。
4. **注册表严格白名单。** `UninstallRegistryPolicy` 只允许 HKCU 下 5 个明确属于 Aurora 的位置：专属设置键、文件关联、卸载登记、App Paths、以及 `Run` 中指向本 EXE 的单一值。`UninstallRegistryService.Scan` 只读展示，`Remove` 删除前再次过白名单；卸载/App Paths 键还要名字含 Aurora 且命令指向本 EXE。绝不写 HKLM，不碰 JavaSoft。
5. **用户确认保持显式。** 卸载窗默认勾选注册表清理，但会显示实际扫描到的项；存档与 Java 仍默认保留，不可恢复确认与二次确认不变。

## 权衡

- 复制 65 MB EXE 到临时目录需要一次磁盘写入；换来的是「卸载后文件真的消失」这一用户最直接可验证的结果。
- 临时清理副本结束后若仍被锁，用 `MoveFileEx` 延迟删除——它在 `%TEMP%`，用户看不到，也不影响卸载目标目录。
- 注册表清理只做已知项，不扫全表；宁可漏掉第三方安装器写下的未知键，也不能误删共享键值。

## 验证与已知限制

- `--unit` 170/170、`--all` 177/177；新增 4 项覆盖注册表白名单与验证、命令行往返、临时进程路径闸门与 2 条静态 Guard。
- **未在真机执行完整卸载**（破坏性操作），用户需先备份存档再实测：EXE 是否立刻消失、数据目录是否还有残留、注册表检测项是否符合预期。
- 清理进程等待父进程最多 15 秒；极端情况下主程序僵死不退出，它会直接开始删文件（此时 EXE 可能仍被锁而删除失败，回退行为由文件系统决定）。
