# ADR-0013：设置脏检查与"任何关闭路径都不能静默丢东西"

- 状态：已采纳（含防线测试 #113–#114）
- 日期：2026-11-14（第 90 轮）
- 相关：ADR-0012（存储清理）、`CloseBehaviorPolicy`（第 74 轮）、`NavigationPolicy`

## 背景

两件事属于同一类失败：**用户做了动作，程序没有确认，结果丢了。**

1. **设置页是"本地修改 + 点保存才生效"**。改完内存、Java 路径，点侧边栏去别的页面，修改静默消失；下次进来还是旧值，用户会认为启动器"忘了"，而不是"我没保存"。
2. **「直接退出」的承诺只在灰色小字里**。第 74 轮的策略确实做到了"有任务时先确认"，但选项本身叫「直接退出」，读起来就是"永远立即关闭"；更糟的是**托盘菜单的退出根本没走这个策略**（`ExitFromTray` 直接 `_shuttingDown = true` 然后关窗），于是选了「直接退出」的用户从托盘退出时，所有下载被静默中断。

## 决策

### 1. 脏检查用快照对比，不用 dirty 标志位

进设置页拍一份快照，保存成功后重拍；`快照 ≠ 当前` 即脏。字段清单集中在一处（`CaptureSettings`），**新增字段自动被覆盖**——这正是不用 18 个 `MarkDirty()` 的理由：漏掉的那个字段就是会丢数据的那个。

代价：快照式比较只能在"取值时"发现变化，所以驱动 UI 提示需要一个刷新源。这里用 500 ms 定时器（只在设置页可见时工作）——因为这些字段大多是纯自动属性，TextBox 往模型里推值，没人发 `PropertyChanged`。给 18 个字段补 setter 只为一个提示不划算。

**关键点：拦截不依赖这个定时器。** `HasUnsavedSettings` 是每次实时算的，哪怕用户在 500 ms 内改完就走，弹窗照样会来。定时器只影响"提示文字多久更新一次"。

### 2. 闸门放在"改页面之前"

`Navigate` 第一句就调 `ConfirmLeaveSettings(target)`，它必须早于 `CurrentPageKey = target`——守卫测试直接断言这个顺序，因为顺序错了功能就静默失效（页面已经切走了，弹窗再问也没意义）。

三个选项的动作：
- **保存并离开** → `ApplySettings()`；如果保存失败（例如存储目录填了无效路径），**留在原页**并说明原因，绝不假装成功。
- **放弃修改** → `LoadSettingsFromConfig()`：只重读配置字段，不调 `LoadAll()`（那会重复往 `ObservableCollection` 里添加账号与实例）。
- **取消** → 什么都不做。

### 3. 关窗也是一条"离开"路径

`OnClosing` 里先问设置，再走下载策略。顺序是有意的：保存很便宜，而在这里选「取消」的用户应该直接留在窗口里，不该再被问一遍下载。

### 4. 托盘退出必须走同一个闸门

新增 `ConfirmExitWithActiveJobs(trigger)`，托盘退出先过它再设 `_shuttingDown`。同时把选项文案改成「直接退出（有下载时仍会确认）」——**文案本身是承诺**，不能只写在下面的说明里。解析器改成前缀匹配，兼容旧文案与旧配置（否则老配置里的「直接退出」会掉回「每次询问我」，等于悄悄改了用户的设置）。

「最小化到托盘」仍然不弹窗：它只收起窗口，下载继续，没有任何东西被中断。**弹窗应该只出现在会丢东西的地方。**

## 后果

- 设置页多了一个 500 ms 的定时器（仅可见时干活，18 条字符串比对），以及一个常驻的橙色提示。
- 每次离开设置页都可能多一次弹窗——只在真的改过东西时。
- 托盘退出多一次确认——只在真的有任务在跑时。
- 三条守卫锁住了容易退化的点：闸门顺序、回滚入口、托盘退出的确认顺序。

## 被否定的方案

- **自动保存（离开即保存）**：设置里有"存储目录"这种需要重启才生效的项，静默保存会让用户以为已经生效；而且自动保存就没有"放弃修改"这个选项了。
- **18 个 `MarkDirty()` setter**：见上，漏一个就是数据丢失点。
- **只在 `OnClosing` 拦、不管托盘**：托盘退出是最容易被当成"随便关一下"的路径，恰恰最需要拦。
- **给「最小化到托盘」也加确认**：没有东西会丢，弹窗只会训练用户盲点「是」。
