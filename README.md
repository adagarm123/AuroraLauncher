# Aurora Launcher

一个从零自研、高性能的 **Minecraft Java 版启动器**（Windows）。

- 技术栈：**.NET 10 / C# 13 + WPF**，UI 与核心逻辑解耦（MVVM）。
- **零外部 NuGet 依赖**：仅使用 .NET 基类库（`System.Text.Json`、`HttpClient`、`System.IO.Compression` 等）。无网络可达性依赖，可离线构建。
- 许可：**MIT**。完全独立实现，未复用 PCL2 / HMCL 等受限制许可证项目的源代码（详见 `LICENSE`）。

## 快速开始

### 方式一：直接运行已发布的可执行文件（推荐）

已生成**单文件、自包含（self-contained）**&#x7684; Windows EXE：

```
publish/AuroraLauncher.exe   (约 63 MB，内含 .NET 运行时不需安装)
```

双击即可在 Windows 10/11 上运行，无需安装 .NET 运行时。首次启动会出现**新手引导**（检测 Java → 推荐版本一键安装 → 完成），老用户自动跳过。

### 方式二：从源码构建

需要安装 [.NET 10 SDK](https://dot.net) 与 Windows（WPF 仅支持 Windows）。

```bash
# 构建桌面程序（Debug）
dotnet build src/AuroraLauncher.Desktop/AuroraLauncher.Desktop.csproj -c Debug

# 发布为单文件自包含 EXE（Release, win-x64）
dotnet publish src/AuroraLauncher.Desktop/AuroraLauncher.Desktop.csproj `
  -c Release -r win-x64 `
  -p:PublishSingleFile=true -p:SelfContained=true `
  -p:IncludeNativeLibrariesForSelfExtract=true `
  -o publish
```

### 运行自测（分层：unit 离线 / all 含网络集成）

```bash
dotnet run --project tests/AuroraSelfTest -c Debug -- --unit   # 25 项，离线、毫秒级、CI 必跑
dotnet run --project tests/AuroraSelfTest -c Debug -- --all    # 38 项，含 7 项网络集成
```

本地一键 CI 脚本：`scripts/run-tests.ps1`（`-Full` 跑全量）；GitHub Actions 见 `.github/workflows/selftest.yml`。

## 安全与合规要点

- **密钥处理**：微软刷新令牌使用 Windows DPAPI（`CryptProtectData` P/Invoke）加密后落盘；访问令牌仅驻留内存、永不写入磁盘。配置中不含任何密钥。
- **TLS**：HTTP 客户端**永不**禁用证书校验。
- **用户数据保护**：实例删除仅在 `instances/` 目录内进行；导入一律**复制**，不触碰源数据。
- **下载源**：默认官方 Mojang/Microsoft；BMCLAPI 镜像由**网络感知自动切换**（用户显式选择永远优先），URL 重写仅作用于已知域名。
- **诊断包隐私**：所有打包文本统一过正则脱敏（token/device_code/Bearer/代理凭据/用户路径，**替换非删除**，保留字段结构），附**脱敏报告**逐文件列明替换处数；日志仅保留末尾 2MB。
- **合规**：见 `LICENSE` —— 未使用 PCL2/HMCL 源码，独立实现；ADR 中有合规决策记录。

## 已知限制

1. **微软登录**：Azure 不允许启动器替用户注册应用，需自备 Client ID（一次性四步配置，**设置页可直接填入**或用环境变量 `AURORA_MICROSOFT_CLIENT_ID`）；未配置时点击登录会显示完整指引而非裸报错。
2. **加载器安装**：Forge/NeoForge 官方安装器需要本机 **Java 21+**（启动器会自动探测）且对应 Maven 仓库可达。
3. **OptiFine**：暂不支持。
4. **CurseForge**：平台未接入（Modrinth 已全覆盖），见 ROADMAP 待办。
5. **BMCLAPI**：作为自动回退/感知源，遵循其服务条款。

## 更新补充（第 28 轮：Fabric 版本解析致命 bug 修复 + 失败状态可视化）

## 更新补充（第 31 轮：实例数据污染根治——"官方 400 / 镜像 404"）

**决定性线索**（失败面板的聚合错误）：官方返回 **400 Bad Request**、BMCLAPI 返回 **404**——不是网络问题，是 **profile URL 本身非法**。

**根因**：实例元数据里的 `LoaderVersion` 字段被旧版本写入**完整版本 ID**（`fabric-loader-0.20.1-1.21`）——`InstallWithLoaderAsync` 曾执行 `LoaderVersion ??= result.VersionId`。拼接出的 profile URL 变成：

```
meta.fabricmc.net/v2/versions/loader/1.21/fabric-loader-0.20.1-1.21/profile/json  → 400/404
```

**修复（三处）**：

1. **清洗加载路径**：`ModLoaderInstaller.InstallAsync` 对传入的 `loaderVersion` 做清洗——完整版本 ID → 提取裸版本号（如 `0.20.1`）；占位文本（"（自动选择最新）"等）→ 视为自动解析；若对应的版本 JSON 已存在则**直接复用不再下载**。
2. **不再污染**：`ModLoaderInstallResult` 新增 `LoaderVersion`（裸版本号），`LauncherService` 不再把 VersionId 写进该字段。
3. **存量数据自愈**：`InstanceManager.LoadAll` 加载时自动清洗遗留脏数据（完整 ID → 裸版本号，占位文本 → null）并写日志，已损坏的实例无需手动处理。

## 更新补充（第 33 轮：ClassNotFoundException 根治——缓存命中未合并继承）

**新日志系统立功**：`[Game] 错误: 找不到或无法加载主类 net.fabricmc.loader.impl.launch.knot.KnotClient`，且启动命令**完全没有 `-cp` 参数**。

**根因**：`VersionResolver.ResolveAsync` 的缓存命中分支直接返回了**未与原版合并的 Fabric profile**——profile JSON 自带 `mainClass`（KnotClient）但没有 `arguments`（jvm 模板含 `${classpath}`）也没有原版的 97 个库，于是：

- 生成的启动命令里没有 `-cp` → JVM 找不到 KnotClient → 退出码 1。

**修复**：缓存命中时若条目带 `inheritsFrom`，**先解析父版本（也走缓存）再执行合并**，得到完整版本（Knot mainClass + 原版 arguments 模板 + 原版 97 库 + Fabric 8 库 + 原版 client jar）。此前网络解析路径（ResolveRecursive）本来就正确合并，只有缓存路径有此缺陷。

补充说明：`ClientJarPath` 与 `GetArtifactPath` 逻辑本就正确（原版 jar 存在时优先使用、无 downloads 的库按 Maven 坐标取路径），合并后 classpath 即完整。

## 更新补充（第 37 轮：微软正版登录修复）

**现象**："微软登录初始化失败: Cannot access a disposed object. Object name: 'System.Net.Http.HttpClient'."

**根因**（HttpClient 生命周期管理缺陷，正是上轮评审关注的"谁可以 dispose"问题）：

1. `AuthService` 在构造时把共享 client **缓存到了字段**（`_http = HttpClientFactory.Instance.Client`）；
2. `LauncherConfig` 每次加载/保存配置都调用 `ConfigureProxy`——**即使代理没变也 dispose 重建**；
3. 于是启动后 Auth 持有的 client 已被释放，微软登录一碰即炸。

**修复**：

- `AuthService` 改为**每次调用即取当前 client**（`Http => HttpClientFactory.Instance.Client`），不再缓存引用；
- `HttpClientFactory.ConfigureProxy` 只在代理**实际变化**时才重建 client，且**不再主动 Dispose 旧实例**（交给 GC，在途请求可安全结束）。

**机制防线新增**（第 19 项自测）：`Guard: shared HttpClient never cached or disposed outside factory`——扫描 `src/`，禁止工厂外的 `_client.Dispose()`、字段缓存共享 client、`using` 包装共享 client。这类 bug 从此无法复发。

**验证**：自测 **19/19 通过**，0 警告 0 错误。

## 更新补充（第 52 轮：下载进度卡死根治——聚合慢速看门狗 + 线路自动切换）

**用户反馈**：安装 Fabric API 前置时进度停在 0%、速度只有 4.9 KB/s，看起来像卡死。

**根因**：内容下载的镜像切换只在整个下载**完全失败**时触发；官方 CDN"慢而不断"（4.9 KB/s 持续爬行）永远不会失败——引擎的 25s 空闲超时也只管"完全没字节"，管不了龟速。结果就是无限爬行。

**修复——聚合慢速看门狗**：
- 新增 `SlowTransferWatcher`（AuroraCore，纯逻辑可单测，时钟注入）：以滚动窗口（5 秒）评估**聚合**速度，连续 4 个窗口均值低于 16 KB/s（约 20 秒）判定为"爬行线路"。
- 用**聚合**速度而非单文件速度：引擎有界并发下一个文件慢是正常的，只有整批都慢才是线路问题。
- `ModManager.DownloadRouteAsync` 把看门狗接入每条线路：判定爬行 → 中止该线路（保留 .part 断点）→ 转为 DownloadException → 既有的 **MCIM 镜像切换**立即接管，镜像线路从断点续传。
- 镜像线路同样受看门狗保护：镜像也爬行则快速失败并给出明确报错（可见的失败优于无声卡死）。
- 阈值/窗口留有充分余量：正常连接的瞬时抖动（20 秒均值后才判定）不会误杀；慢速启动有 20 秒宽限。

**防线**：新增单测第 29 项 `SlowTransferWatcher: sustained crawl aborts, brief dips don't`（持续爬行必中止 / 恢复后计数归零不误杀，纯逻辑含注入时钟）。

## 更新补充（第 57 轮：新功能——自动更新上线）

**ROADMAP「自动更新 + 签名验证」正式落地**（详见 [docs/auto-update.md](docs/auto-update.md)）。

**用户体验**：启动器每次打开静默检查更新（8 秒超时，失败即静默跳过）→ 发现新版本 → 非阻塞 toast 提示 → 后台下载到 `存储目录/update/` 并 **SHA-256 校验** → toast「新版本已就绪」→ **用户下次启动时自动换装并重启**——全程只需重启一次，不再手动去网盘下载替换。设置页新增「更新」卡片（自动检查开关 + 检查更新按钮）。

**安全模型**：
- **防篡改**：更新清单 latest.json 携带 **RSA-4096 签名**（覆盖 round|version|url|sha256|size），公钥内嵌于 UpdateService——清单被篡改或中间人替换一律验签失败、静默忽略；
- **防降级**：只有 round **严格大于** `BuildInfo.CurrentRound` 的清单才算更新；
- **下载校验**：引擎断点续传 + 清单 SHA-256 复核；
- **换装机制**：运行中的 EXE 被锁定——重启时由一个分离的 cmd 脚本（带 10 次重试）完成覆盖并重新启动。

**发布者流程**（docs/auto-update.md）：`publish.ps1` → `sign-release.ps1 -DownloadUrl <托管地址>`（自动读 BuildInfo.Round、签名生成 latest.json）→ 上传 EXE + latest.json 到任意静态 HTTPS 托管（Gitee Releases / GH 加速 / OSS 等）→ 把 latest.json 地址填入 `UpdateService.DefaultFeedUrl`（一行常量，当前为空 = 检查关闭，填写后生效）。签名私钥在 `scripts/signing/`（保密，勿外发）。

**配套改动**：`BuildInfo.CurrentRound` 常量（发布时 bump）并纳入文档基线 Guard（docs 轮次 ≠ BuildInfo 即红——本次运行已实际抓到一次漏 bump）；新增单测 #31（验签通过 / 篡改 url|sha|size|round 任一字段必失败 / 防降级规则）；`SlowTransferKBsPerSec` 等配置项化；应用内更新日志新增第 57 轮条目。

自测 **Unit 31/31** 全绿；EXE 经 `publish.ps1` 重新发布。
